# دليل النشر الآمن على Railway

**الفكرة الأساسية:** الترحيل `004` إضافي بالكامل، والكود القديم يعمل معه دون أي تعديل (اختُبر: اختبار M6 يدرج عميلًا بالطريقة القديمة بعد الترحيل فيحصل على رقم تلقائيًا). لذلك ترتيب النشر الآمن هو:

> نسخة احتياطية ← تجربة كاملة على بيئة منفصلة ← **ترحيل الإنتاج والكود القديم ما زال يعمل** ← نشر الكود الجديد ← تحقق ← (رجوع بنقرة إن لزم)

لا أضمن "صفر انقطاع": Railway يبني حاوية جديدة ثم يبدّل، وقد تفشل طلبات قليلة أثناء التبديل. التطبيق على Windows يعيد المحاولة غالبًا، لكن هذا لم يُختبر عندي (لا أملك كود العميل). انشر في وقت هادئ.

---

## 0) قبل أي شيء
- لا تُشغّل أي أمر من هذا الدليل على الإنتاج قبل أن تنجح الخطوات 1–4.
- الملف المرفق عندي كان يحتوي `.env` ونسخة SQL. **لم أستخدمهما ولم أُدرجهما في ZIP الناتج.** إن كان ZIP الأصلي قد شورك مع أحد، دوّر `JWT_SECRET` وكلمة مرور الإدارة وكلمة مرور قاعدة البيانات.

## 1) نسخة كاملة من الإصدار الحالي
```
git status                      # يجب أن يكون نظيفًا (أو التزم بما لديك أولًا)
git tag pre-customer-mgmt
git push origin pre-customer-mgmt
git branch backup/pre-customer-mgmt && git push origin backup/pre-customer-mgmt
```
وفي Railway: اترك النشر الحالي كما هو في قائمة Deployments (يمكن إعادة نشره لاحقًا من هناك). دوّن الآن **أمر التشغيل (Start Command)** المضبوط في إعدادات الخدمة، فقد أضفتُ `"start": "node src/index.js"` إلى `package.json` ولا أعرف ما هو مضبوط عندك.

## 2) نسخة احتياطية من PostgreSQL والتحقق من استعادتها
من جهازك، باستخدام رابط الاتصال **العام** لخدمة قاعدة البيانات (من Railway → خدمة Postgres → Variables/Connect):
```
# اعرف إصدار الخادم أولًا، وليكن pg_dump بنفس الإصدار أو أحدث
psql "$PROD_URL" -Atc "select version()"

pg_dump "$PROD_URL" --format=custom --no-owner --no-privileges -f prod-before-004.dump
```
**تحقق من الاستعادة (إلزامي):**
```
createdb restore_check
pg_restore --no-owner -d restore_check prod-before-004.dump
psql restore_check -c "select (select count(*) from licenses) l, (select count(*) from devices) d, (select count(*) from activations) a, (select count(*) from customers) c"
```
قارن الأعداد بقاعدة الإنتاج نفسها (`select count(*)` بنفس الاستعلام). احفظ الملف في مكانين خارج المستودع (لا تضعه في Git؛ فيه بيانات عملاء).

## 3) خدمة اختبار وقاعدة منفصلة
في Railway أنشئ **بيئة جديدة** (Environment) أو مشروعًا منفصلًا فيه:
1. خدمة PostgreSQL جديدة (فارغة).
2. خدمة التطبيق من نفس المستودع على فرع الميزة الجديدة، و`DATABASE_URL` فيها تشير إلى **قاعدة الاختبار فقط**.
3. استعد فيها نسخة الإنتاج: `pg_restore --no-owner -d "<رابط قاعدة الاختبار العام>" prod-before-004.dump`
4. **لا تنسخ** مفاتيح الدفع الحقيقية إلى بيئة الاختبار (انظر البند 4).

## 4) متغيرات البيئة دون كشف الأسرار
القائمة الكاملة في `docs/ENV_VARS.md`. قواعد:
- أدخلها من واجهة Railway (Variables) فقط. لا تضعها في Git ولا في لقطات شاشة ولا في الدردشة.
- بيئة الاختبار: `JWT_SECRET` و`ADMIN_PASSWORD_HASH` **مختلفان** عن الإنتاج. اترك `PADDLE_*` فارغة (أو مفاتيح sandbox) كي لا يمكن لأحد إجراء دفع حقيقي.
- ولّد الأسرار محليًا بأوامر `.env.example`.

## 5) اختبر الإصدار الجديد قبل النشر
على بيئة الاختبار (نسخة من بيانات الإنتاج):
```
DATABASE_URL=<قاعدة الاختبار على Railway> npm run migrate:plan     # راجع الأرقام المقترحة لكل عميل
DATABASE_URL=<قاعدة الاختبار على Railway> npm run migrate:apply
```
ثم تحقق يدويًا:
- `GET /health` ← `database: connected`.
- سجّل دخول `/admin`: الجدول يظهر، الأعداد في الأعلى تطابق ما تعرفه.
- كل عميل قديم له رقم، والتراخيص القديمة بلا عميل تظهر كـ«ناقص» وبزر «استكمال البيانات».
- أنشئ دفعة تجريبية (3 تراخيص) **في بيئة الاختبار** وجرّب من برنامج Windows موجّهًا إلى عنوان بيئة الاختبار: تفعيل/تحقق/إلغاء تفعيل.
- جرّب Excel وCSV وافتحهما بالعربية.

## 6) تطبيق الترحيل على الإنتاج (بعد المراجعة)
الكود القديم ما زال يعمل أثناء هذه الخطوة.
```
# 1. تجربة جافة على الإنتاج: تنفّذ داخل معاملة ثم تتراجع (تأخذ قفلًا قصيرًا جدًا على customers)
DATABASE_URL=<إنتاج> npm run migrate:plan
```
تحقق من: «Protected tables … identical before/after» ومن قائمة الأرقام (العميل الأقدم = #1 … بالترتيب حسب `created_at` ثم `id`). **هذا الترقيم يحدث مرة واحدة ويصبح دائمًا**، فاعتمده فقط إن كان مقبولًا.
```
# 2. التطبيق الفعلي
DATABASE_URL=<إنتاج> npm run migrate:apply
```
الأداة تنفّذ كل شيء في معاملة واحدة، وتقارن بصمة (عدد الصفوف + md5 للمحتوى) لجداول `licenses` و`devices` و`activations` و`products` قبل وبعد، **وتتراجع تلقائيًا** عند أي اختلاف أو خطأ. إن فشلت: لا شيء تغيّر؛ لا تحتاج استعادة، أرسل لي رسالة الخطأ.

بديل يدوي: `psql "$DATABASE_URL" --single-transaction -v ON_ERROR_STOP=1 -f src/db/004_customer_management.sql`

## 7) نشر الكود الجديد
ادمج الفرع في الفرع المنشور (أو أعد ربط الخدمة بالفرع الجديد). راقب سجل البناء حتى يصبح `Active`. **لا تحذف** الخدمة القديمة أو أي نشر سابق أو أي قاعدة بيانات فور النشر؛ اتركها أيامًا.

## 8) التحقق بعد النشر (دون إنشاء بيانات تجريبية في الإنتاج)
1. `GET /health` ← `status: ok`.
2. لوحة الإدارة: إجمالي التراخيص يساوي ما سجّلته قبل الترحيل.
3. افتح **نسختك الحقيقية** من برنامج Windows المفعّلة: يجب أن تتحقق كالمعتاد (هذا تحقق حقيقي بلا بيانات جديدة).
4. طلب بلا كتابة: `POST /api/v1/licenses/validate` بمفتاح وهمي يجب أن يعيد `{"status":"invalid","message":"License is not active on this device."}`.
5. في السجلات (Railway → Logs) ابحث عن `error` في الدقائق الأولى.
6. شاهد أول عملية بيع حقيقية: يجب أن يظهر العميل في الجدول برقم جديد (التالي في التسلسل).
